# API v2 Documentation: Authentication and Extended Payment Features

## 1. Overview

This document details a significant upgrade to our API, introducing **API v2**. This version enhances our payment processing capabilities by integrating robust security features, standardizing API interactions, and expanding the suite of payment-related functionalities.

The primary motivations for this change are:
*   **Enhanced Security**: Implementing mandatory API key authentication for all endpoints to protect sensitive operations.
*   **Improved API Design**: Introducing versioning and standardizing API response structures for greater consistency and developer experience.
*   **Expanded Functionality**: Adding crucial features for customer management, comprehensive payment intent lifecycle management, order retrieval, and refund processing.

This is a comprehensive API version upgrade that introduces critical security features, improves API design consistency, and expands functionality, necessitating significant adaptations for all API consumers and server implementations.

## 2. Impact

This change represents a major architectural shift, affecting various parts of our system and the developer experience for API consumers.

### Impact Scope:
*   **API Versioning**: All API endpoints are now versioned under `/api/v2/`.
*   **Authentication**: All API requests now require authentication.
*   **API Security**: Enhanced security through API key validation.
*   **Payment Processing**: Significant expansion of payment-related operations.
*   **Customer Management**: Introduction of customer creation capabilities.
*   **Developer Experience**: Standardized responses and clear versioning aim to improve interaction with the API, despite initial migration effort.

### Affected Components:
*   `payment-element/server/*`: All server-side API implementations have been updated to reflect API v2 changes, including new endpoints, authentication, and response structures.
*   `payment-element/client/*`: Frontend client applications have been modified to interact with the new API v2 endpoints, adopt new request methods, and include authentication headers.
*   `.env.example`: Updated to include the new `API_SECRET_KEY` environment variable.
*   `API_V2_MIGRATION.md`: A dedicated migration guide has been created to assist existing clients.
*   `payment-element/server/nextjs/lib/auth.ts`: A new module introduced to handle API key validation.

## 3. New Features

API v2 introduces a range of new capabilities and structural improvements:

*   **API Key Authentication**: All API endpoints now require an `X-API-Key` header for authentication.
*   **API Versioning**: All routes are now prefixed with `/api/v2/` to ensure clear versioning and allow for future API evolution.
*   **Standardized API Response Structure**: All API responses now follow a consistent JSON format:
    ```json
    {
      "success": true, // or false
      "data": { /* resource-specific data on success */ },
      "error": { // present only if success is false
        "code": "ERROR_CODE",
        "message": "Detailed error message",
        "details": { /* additional error specifics */ }
      }
    }
    ```
*   **`POST /api/v2/customers`**: Creates a new customer record.
*   **`GET /api/v2/payment-intent/:id`**: Retrieves the status and details of a specific payment intent.
*   **`POST /api/v2/refunds`**: Processes a refund for a previously successful payment.
*   **`GET /api/v2/orders/:id`**: Retrieves the details of a specific order.
*   **`POST /api/v2/payment-intent/:id/confirm`**: Explicitly confirms a payment intent, typically after client-side payment method collection.

## 4. Breaking Changes and Migration Preparations

This release introduces significant breaking changes that require all existing API consumers to update their integrations.

### 4.1. API Versioning
*   **Change**: All existing API endpoints are now deprecated in their unversioned form and have been moved under the `/api/v2/` prefix.
*   **Impact**: Any request to the old unversioned paths (e.g., `/api/create-payment-intent`) will no longer work.
*   **Migration**: Update all API request URLs to include the `/api/v2/` prefix (e.g., `/api/v2/create-payment-intent`).

### 4.2. Mandatory API Key Authentication
*   **Change**: All API v2 endpoints now require an `X-API-Key` header with a valid API secret key.
*   **Impact**: Unauthenticated requests will receive a `401 Unauthorized` response.
*   **Migration**:
    *   Configure `API_SECRET_KEY` in your backend environment variables (see `.env.example`).
    *   Include an `X-API-Key` header with your configured `API_SECRET_KEY` in all API requests.

### 4.3. `create-payment-intent` Endpoint Change
*   **Change**: The `create-payment-intent` endpoint has been converted from a `GET` request to a `POST` request. It now expects `amount` and `currency` in the request body, not as query parameters.
*   **Impact**: Existing `GET` requests will fail.
*   **Migration**:
    *   Change the HTTP method from `GET` to `POST`.
    *   Move `amount` and `currency` from query parameters to the JSON request body.

### 4.4. Standardized API Responses
*   **Change**: All API responses now adhere to the standardized `{ success, data, error }` JSON structure.
*   **Impact**: Clients parsing previous response formats (e.g., direct data return, different error structures) will need to adjust their parsing logic.
*   **Migration**: Update client-side code to expect and parse the new standardized response format. Always check the `success` field before attempting to access `data` or `error`.

### 4.5. Environment Variables
*   **Change**: A new environment variable, `API_SECRET_KEY`, is required for server-side API key validation.
*   **Impact**: Servers will fail to start or API authentication will fail if this variable is not set.
*   **Migration**: Add `API_SECRET_KEY` to your `.env` file or environment configuration.

## 5. Technical Details

### 5.1. API Versioning
All API endpoints are now designed with explicit versioning using the `/api/v2/` path prefix. This approach ensures backward compatibility for future API changes and allows for a clear transition path.

### 5.2. API Key Authentication
*   **Mechanism**: A mandatory `X-API-Key` HTTP header must be present in every request to API v2 endpoints.
*   **Validation**: The value of `X-API-Key` is validated against the `API_SECRET_KEY` environment variable configured on the server.
*   **Implementation**: A new utility module, `payment-element/server/nextjs/lib/auth.ts`, handles the extraction and validation of the API key for Next.js backend implementations. Similar authentication middleware or functions have been implemented across other backend frameworks (e.g., Node.js, Python, Ruby).

### 5.3. Standardized Response Structure
To improve consistency and predictability, all API v2 endpoints return JSON responses in the following format:
```json
{
  "success": boolean, // true if the operation was successful, false otherwise
  "data": object | null, // The result of the operation on success, or null if an error occurred
  "error": { // Present only when 'success' is false
    "code": string, // A specific error code (e.g., "INVALID_API_KEY", "MISSING_PARAMETER", "PAYMENT_FAILED")
    "message": string, // A human-readable description of the error
    "details": object | null // Optional additional details about the error (e.g., validation errors)
  }
}
```
This structure allows clients to easily determine the outcome of an API call and handle errors consistently.

### 5.4. `create-payment-intent` Evolution
The `create-payment-intent` endpoint has been redesigned from `GET` to `POST` to better align with REST best practices for resource creation and to safely transmit sensitive data (like amount and currency) in the request body, rather than URL query parameters.

### 5.5. New Endpoint Implementations
The newly introduced endpoints (`/customers`, `/payment-intent/:id`, `/refunds`, `/orders/:id`, `/payment-intent/:id/confirm`) integrate deeply with the payment processing backend, providing a more granular control over the payment lifecycle and customer management. Each endpoint includes appropriate business logic, error handling, and data validation.

## 6. Usage Examples

Below are examples demonstrating how to interact with API v2 endpoints, assuming a `fetch` or `axios` like client in JavaScript. Replace `YOUR_API_SECRET_KEY` with your actual key and `YOUR_BACKEND_URL` with your server's base URL.

First, ensure your server has `API_SECRET_KEY` configured in its environment, e.g., in `.env`:
```
API_SECRET_KEY=sk_test_YOUR_GENERATED_SECRET_KEY
```

### 6.1. General Authenticated Request Structure

```javascript
const YOUR_API_SECRET_KEY = 'sk_test_YOUR_GENERATED_SECRET_KEY';
const YOUR_BACKEND_URL = 'http://localhost:4242'; // Or your deployed backend URL

async function makeAuthenticatedRequest(endpoint, method = 'GET', body = null) {
  const headers = {
    'Content-Type': 'application/json',
    'X-API-Key': YOUR_API_SECRET_KEY,
  };

  const options = {
    method: method,
    headers: headers,
  };

  if (body) {
    options.body = JSON.stringify(body);
  }

  try {
    const response = await fetch(`${YOUR_BACKEND_URL}/api/v2${endpoint}`, options);
    const data = await response.json();

    if (!response.ok || !data.success) {
      console.error('API Error:', data.error || data);
      throw new Error(data.error?.message || `API request failed with status ${response.status}`);
    }
    return data.data;
  } catch (error) {
    console.error('Network or Parsing Error:', error);
    throw error;
  }
}
```

### 6.2. Create Customer (`POST /api/v2/customers`)

```javascript
async function createCustomer(email, name) {

    '/customers',
```

## 8. API v2 Migration Guide for Existing Clients

This guide outlines the essential steps for existing API clients to migrate to API v2. It is crucial to follow these steps to ensure continued functionality.

### Step 1: Update API Endpoints

All API requests must now target the `/api/v2/` prefix.

**Before (API v1 - Example):**
```
GET /api/create-payment-intent?amount=1099&currency=usd
```

**After (API v2):**
```
POST /api/v2/create-payment-intent
```
(Note: Method and body also changed, see Step 3)

**Action:** Review all API calls in your client application and update their URLs to include `/api/v2/`.

### Step 2: Implement API Key Authentication

All API v2 requests require an `X-API-Key` header for authentication.

**Action:**
1.  **Generate/Obtain API Key**: Ensure you have a valid `API_SECRET_KEY` configured in your backend environment (e.g., `API_SECRET_KEY=sk_test_your_secret_key`). This key will be used by your client to authenticate.
2.  **Include Header**: Add the `X-API-Key` header with your secret key to all your API requests.

**Example (JavaScript `fetch`):**
```javascript
const YOUR_API_SECRET_KEY = 'sk_test_your_secret_key'; // Use environment variable or secure method to store/retrieve this
const response = await fetch('YOUR_BACKEND_URL/api/v2/create-payment-intent', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-API-Key': YOUR_API_SECRET_KEY, // Add this line
  },
  body: JSON.stringify({ amount: 1099, currency: 'usd' }),
});
```

### Step 3: Adjust `create-payment-intent` Request

The `create-payment-intent` endpoint has changed significantly.

**Before (API v1):**
*   **Method**: `GET`
*   **Parameters**: `amount`, `currency` as URL query parameters.

```javascript
// Example v1 GET request
fetch('/api/create-payment-intent?amount=1099&currency=usd');
```

**After (API v2):**
*   **Method**: `POST`
*   **Parameters**: `amount`, `currency` (and optionally `customerId`) in the JSON request body.

**Action:** Update your `create-payment-intent` call to use `POST` and pass parameters in the request body.

**Example (JavaScript `fetch`):**
```javascript
const response = await fetch('YOUR_BACKEND_URL/api/v2/create-payment-intent', {
  method: 'POST', // Changed from GET to POST
  headers: {
    'Content-Type': 'application/json',
    'X-API-Key': YOUR_API_SECRET_KEY,
  },
  body: JSON.stringify({
    amount: 1099, // In request body
    currency: 'usd', // In request body
    // customerId: 'cus_xyz123' // Optional
  }),
});
```

### Step 4: Update API Response Parsing

All API v2 responses now follow a consistent `{ success, data, error }` JSON structure.

**Before (API v1 - Example):**
A successful response might directly return the data:
```json
{
  "clientSecret": "pi_xyz_secret_abc"
}
```
An error might be a direct message or different structure:
```json
{
  "message": "Invalid amount"
}
```

**After (API v2):**
A successful response will wrap data in a `data` object:
```json
{
  "success": true,
  "data": {
    "clientSecret": "pi_xyz_secret_abc",
    "id": "pi_xyz"
  },
  "error": null
}
```
An error response will be structured under an `error` object:
```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Amount must be a positive integer.",
    "details": { "field": "amount" }
  }
}
```

**Action:** Update your client-side code to parse this new structure. Always check `response.json().success` before accessing `response.json().data` or `response.json().error`.

**Example (JavaScript):**
```javascript
const response = await fetch('...');
const result = await response.json();

if (result.success) {
  // Access data here
  console.log('Success:', result.data);
  const clientSecret = result.data.clientSecret;
  // ... proceed with clientSecret
} else {
  // Handle error here
  console.error('API Error:', result.error.message, result.error.code);
  // Display error to user, log details
}
```

### Step 5: Configure `API_SECRET_KEY` on your Server

If you are running a server-side component that interacts with the payment provider, it will need the `API_SECRET_KEY` configured.

**Action:** Add `API_SECRET_KEY` to your server's `.env` file or environment variables. This key is used for validating incoming API requests to your own backend endpoints.

**Example `.env` file:**
```
API_SECRET_KEY=sk_test_YOUR_GENERATED_SECRET_KEY
```
