## API v2.0 Documentation

### 1. Overview

This release marks a significant upgrade to our API, introducing a new major version (v2.0) with a strong focus on security, consistency, and expanded functionality. The primary driver for this update is to establish a secure and robust foundation for future API development, enhance the developer experience through standardization, and introduce advanced payment processing capabilities.

Key changes include mandatory API key authentication for all v2 endpoints, standardized JSON response formats across the API, and a complete re-routing of all existing endpoints under the `/api/v2/` prefix. Additionally, several new payment-related functionalities have been added, and the core payment intent creation process has been refined.

### 2. Impact

This change represents a fundamental shift in how our API is consumed and integrated, affecting various components across the system and client integrations.

**Impact Scope:**
*   API Security
*   API Design & Standards
*   Payment Processing Logic
*   Client Integrations (Frontend & Backend)
*   Developer Experience & Documentation

**Affected Components:**
*   **API Gateway/Routing**: All API routes have been updated and prefixed.
*   **Authentication Middleware**: New middleware implemented to enforce API key checks.
*   **Payment Intent Creation Logic**: Updated for new parameters and response.
*   **Customer Management**: New dedicated endpoint for customer creation.
*   **Refund Processing**: New dedicated endpoint for refunds.
*   **Order Management**: New dedicated endpoint for order retrieval.
*   **Configuration**: New environment variables (`API_VERSION`, `API_SECRET_KEY`).
*   **Frontend Client Examples**: HTML and React examples updated to reflect v2.
*   **Backend Server Implementations**: Java, Node.js, Next.js, Python, Ruby backend servers updated.
*   **Documentation**: This documentation, API reference, and a dedicated migration guide (`API_V2_MIGRATION.md`).

### 3. New Features

API v2.0 introduces several new capabilities and improvements:

*   **API Key Authentication**: All routes under `/api/v2/` now require an `X-API-Key` header for authentication, significantly enhancing API security.
*   **API Versioning**: All API endpoints are now consistently prefixed with `/api/v2/`, providing clear versioning and facilitating future upgrades.
*   **Standardized API Response Structure**: All successful and error API responses now adhere to a consistent JSON format:
    ```json
    // Success Response
    {
      "success": true,
      "data": {
        // resource-specific data
      }
    }

    // Error Response
    {
      "success": false,
      "error": {
        "code": "ERROR_CODE",
        "message": "A descriptive error message.",
        "details": {} // Optional additional details
      }
    }
    ```
*   **Dedicated API Endpoint for Creating Stripe Customers**:
    *   `POST /api/v2/customers`
    *   Allows for programmatically creating and managing customer records within Stripe.
*   **Dedicated API Endpoint for Retrieving Payment Intent Status**:
    *   `GET /api/v2/payment-intent/:id`
    *   Provides a simple way to fetch the current status and details of a specific payment intent.
*   **Dedicated API Endpoint for Processing Refunds**:
    *   `POST /api/v2/refunds`
    *   Enables processing refunds for previously completed payments.
*   **Dedicated API Endpoint for Retrieving Order Details**:
    *   `GET /api/v2/orders/:id`
    *   Fetches comprehensive details for a specific order.
*   **Updated `/create-payment-intent` Endpoint**:
    *   Now uses a `POST` method.
    *   Requires `amount` (in cents) and `currency` (e.g., "usd") in the request body.
    *   Provides an extended response object, including `clientSecret`, `paymentIntentId`, and `amount`.

### 4. Breaking Changes

API v2.0 introduces several breaking changes that require updates to existing client integrations:

*   **Mandatory API Key Authentication**: All requests to `/api/v2/` endpoints **must** include a valid API key in the `X-API-Key` HTTP header. Requests without this header or with an invalid key will be rejected with a `401 Unauthorized` or `403 Forbidden` error.
*   **API Endpoint Path Changes**: All previous API endpoint paths (e.g., `/config`, `/create-payment-intent`) are now prefixed with `/api/v2/`.
    *   `GET /config` -> `GET /api/v2/config`
    *   `GET /create-payment-intent` -> `POST /api/v2/create-payment-intent`
    *   All other previously custom routes now follow this `/api/v2/` convention.
*   **`create-payment-intent` Method and Request Body Change**:
    *   The `/api/v2/create-payment-intent` endpoint has changed from a `GET` request to a `POST` request.
    *   It now requires `amount` (integer, in smallest currency unit, e.g., cents for USD) and `currency` (string, e.g., "usd") in the JSON request body, instead of query parameters.
*   **Standardized Response Format**: All API responses have been unified into the `{"success": boolean, "data": {}, "error": {}}` structure. Clients must adapt their parsing logic to handle this new format, accessing data via the `data` field and error details via the `error` field.

### 5. Technical Details

*   **Environment Variables**:
    *   `API_VERSION=2.0.0` has been introduced to denote the current API version.
    *   `API_SECRET_KEY` is now a mandatory environment variable in the `payments-backend` repository, used by the authentication middleware to validate incoming requests.
*   **Authentication Middleware**: A robust API key authentication middleware has been implemented across all backend server implementations (Java, Node.js, Next.js, Python, Ruby). This middleware intercepts all requests to `/api/v2/` routes, verifies the `X-API-Key` header against `API_SECRET_KEY`, and denies access if invalid or missing.
*   **Routing Updates**: The API Gateway and individual backend services have been configured to handle the new `/api/v2/` prefix for all API routes. This involved updating routing configurations and endpoint definitions in each service.
*   **`create-payment-intent` Endpoint Refinement**:
    *   The endpoint logic was updated to reflect the `POST` method and parse `amount` and `currency` from the request body.
    *   The response object for `create-payment-intent` has been extended to include `clientSecret`, `paymentIntentId`, and `amount`, providing more comprehensive information directly.
*   **New RESTful Endpoints**: Dedicated controllers and service logic have been developed for the new `customers`, `payment-intent/:id`, `refunds`, and `orders/:id` endpoints, following RESTful principles for resource management.
*   **Client-Side Examples**: The provided `HTML` and `React` frontend client examples have been fully updated to interact with the authenticated v2 API endpoints, demonstrating how to include the `X-API-Key` header and handle the new request/response structures.

### 6. Usage Examples

Here are examples of how to interact with the new API v2.0 endpoints:

#### 6.1. API Key Authentication

All requests to v2 endpoints must include the `X-API-Key` header.
Replace `YOUR_API_SECRET_KEY` with your actual key.

```bash
# Example using curl
curl -X GET "https://api.example.com/api/v2/config" \
     -H "X-API-Key: YOUR_API_SECRET_KEY"
```

```javascript
// Example using JavaScript fetch
fetch('https://api.example.com/api/v2/config', {
  method: 'GET',
  headers: {
    'X-API-Key': 'YOUR_API_SECRET_KEY',
    'Content-Type': 'application/json'
  }
})
.then(response => response.json())
.then(data => console.log(data));
```

#### 6.2. Create Payment Intent (`POST /api/v2/create-payment-intent`)

```bash
curl -X POST "https://api.example.com/api/v2/create-payment-intent" \
     -H "X-API-Key: YOUR_API_SECRET_KEY" \
     -H "Content-Type: application/json" \
     -d '{
           "amount": 2000,
           "currency": "usd"
         }'
```

**Example Response:**
```json
{
  "success": true,
  "data": {
```

### 7. Testing

To ensure a smooth transition and verify the correct implementation of API v2.0, the following testing procedures are recommended:

*   **API Key Authentication**:
    *   Verify that all `/api/v2/` endpoints correctly reject requests without an `X-API-Key` header.
    *   Verify that requests with an invalid `X-API-Key` are rejected.
    *   Confirm that requests with a valid `X-API-Key` are successfully authenticated.
    *   Test both `GET` and `POST` methods with authentication.
*   **Endpoint Routing**:
    *   Ensure all previous API paths (e.g., `/config`) now correctly respond only under `/api/v2/config`.
    *   Verify that old, unversioned paths return `404 Not Found` or appropriate deprecation messages.
*   **`POST /api/v2/create-payment-intent`**:
    *   Test with valid `amount` and `currency` in the request body.
    *   Verify the response structure and the presence of `clientSecret`, `paymentIntentId`, and `amount`.
    *   Test with missing or invalid `amount`/`currency` to ensure proper error handling.
*   **New Endpoints (`/customers`, `/payment-intent/:id`, `/refunds`, `/orders/:id`)**:
    *   Thoroughly test each new endpoint with valid and invalid parameters.
    *   Verify successful creation, retrieval, or processing, and check the response data against expected outcomes.
    *   Test edge cases (e.g., non-existent `payment_intent_id` for refund, invalid `customer_id`).
*   **Standardized Response Format**:
    *   For all endpoints (new and updated), verify that both success and error responses adhere to the `{"success": boolean, "data": {}, "error": {}}` structure.
    *   Check for appropriate error codes and messages in error responses.
*   **Client-Side Integrations**:
    *   Test the updated HTML and React frontend examples to ensure they correctly interact with the v2 API, including authentication and new response parsing.
    *   If applicable, test any existing client applications that have been migrated to v2 to confirm full compatibility.
*   **Backend Implementations**:
    *   Ensure all backend server implementations (Java, Node.js, Next.js, Python, Ruby) correctly enforce authentication, process requests, and generate v2-compliant responses.
    *   Verify that environment variables (`API_VERSION`, `API_SECRET_KEY`) are correctly loaded and utilized.

### 8. Migration Guide

Migrating to API v2.0 requires careful consideration and updates to your existing integrations. A detailed `API_V2_MIGRATION.md` guide has been provided within the repository for comprehensive step-by-step instructions. Below is a summary of the key migration steps:

**Prerequisites:**
*   Ensure your backend environment has the new `API_VERSION=2.0.0` and `API_SECRET_KEY` environment variables configured.
*   Generate a new `API_SECRET_KEY` for your integration; *do not* use development keys in production.

**Migration Steps:**

1.  **Update API Endpoint Paths**:
    *   Prefix all your existing API calls with `/api/v2/`.
    *   For example, if you were calling `/create-payment-intent`, you must now call `/api/v2/create-payment-intent`.

2.  **Implement API Key Authentication**:
    *   For every request to an `/api/v2/` endpoint, add an `X-API-Key` HTTP header.
    *   The value of this header must be your `API_SECRET_KEY`.

3.  **Adapt `create-payment-intent` Endpoint Usage**:
    *   **Change HTTP Method**: Update your client code to use `POST` instead of `GET` for `/api/v2/create-payment-intent`.
    *   **Modify Request Body**: Instead of sending `amount` and `currency` as query parameters, send them as a JSON object in the request body.
        ```json
        {
          "amount": 2000,
          "currency": "usd"
        }
        ```
    *   **Update Response Handling**: The response object is now standardized. Access `clientSecret` and other data via the `data` field of the response.

4.  **Update API Response Handling**:
    *   All API responses now follow the standardized `{"success": boolean, "data": {}, "error": {}}` structure.
    *   Adjust your client-side parsing logic to check the `success` field. If `true`, access the payload from the `data` object. If `false`, retrieve error details from the `error` object.

5.  **Integrate New Functionality (Optional but Recommended)**:
    *   Explore and integrate the new dedicated endpoints for `customers`, `payment-intent/:id`, `refunds`, and `orders/:id` as needed for enhanced payment management and user experience.

**Reference:**
For a comprehensive, detailed migration walkthrough, please refer to the `API_V2_MIGRATION.md` guide provided in the root of the `payments-backend` repository.
